# 实际业务验收：测试管理平台

用户于 2026-10-08 明确授权使用本地现有测试管理平台，执行“登录 → 创建项目/用例 → 查询”，使用独立测试数据。本场景调用平台的实际 Express 路由及 PostgreSQL，不使用演示 HTTP 服务。

## 规则与资料来源

规则基线：本仓库 `d2de8ab` 的路由实现。下列说明为从现有代码核对形成的接口资料，非外部需求规格；验收反映该版本已实现的规则，不能证明这些规则完全覆盖学校或其他客户的业务需求。

| 接口                        | 确认的规则                                                                                          | 代码来源                                      |
| --------------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| POST `/users/signin`        | email/password 正确为 200，返回 access_token；错误密码为 401 / Authentication failed                | [登录](../backend/routes/users/signin.js)     |
| POST `/projects`            | 已登录用户创建项目，返回 200 和项目对象；userId 来自登录身份                                        | [创建项目](../backend/routes/projects/new.js) |
| POST `/folders?projectId=…` | 项目开发者及以上创建目录；name 必填，成功为 200                                                     | [创建目录](../backend/routes/folders/new.js)  |
| POST `/cases?folderId=…`    | title/state/priority/type/automationStatus/template 不得缺失或为 null；缺失返回 400；创建成功为 200 | [创建用例](../backend/routes/cases/new.js)    |
| GET `/cases/:caseId`        | 登录用户有项目可见权限时返回保存的用例及关联记录，成功为 200                                        | [查询用例](../backend/routes/cases/show.js)   |

项目所有者拥有所需访问权限；凭据不正确不能获得有效 Token。认证和项目权限沿用原中间件。自动化不自行猜测 201 或其他通用约定，以该项目明确实现为准。

## 冻结用例与数据

[cases.json](cases.json) 是两种流程共同使用的请求、断言和依赖基线。10 条用例预期为 **7 通过、2 失败、1 未执行**。

- 正常链路：1 登录 → 2 创建私有项目 → 3 创建目录 → 4 创建用例 → 5 查询。
- 负向业务输入：6 错误密码应返回 401；7 缺少标题应返回 400。这两条满足错误处理规则时应通过。
- 控制实验：8 故意破坏登录前置，应失败；9 依赖它，应跳过；10 故意设置错误标题预期，应失败。这些故障注入不算发现真实产品缺陷。
- 测试账号通过平台管理员创建，为独立普通用户，不复用管理员作为被测业务身份。密码随机生成，只保存在被 Git 忽略的本地文件/后端环境变量；Token 每轮实际登录获取。
- 每个模式、每轮创建不同名称的私有项目，目录与用例从空项目开始。所有 ID 从真实响应提取，不填写固定数据库编号。测试数据保留供追溯，不清空已有项目。
- 首次 Agent 准备时，故意不保存第 5 条的执行配置，以验证明确缺失信息、按文档补充与保存复用。用例及预期保持冻结；这是预设的缺失信息检查，不代表真实测试人员一定会遗漏该配置。

## 测量边界

准备命令：先按根 README 启动数据库及后端，再在仓库根目录执行 `node business/prepare.mjs`。脚本通过真实管理接口建立独立账号、用例和六个运行，凭据写入已忽略的 `business/.env.study.json`；脚本在配置运行环境之前，将允许来源、认证变量和本项目密钥授权写入后端 `.env`。首次配置环境若提示未授权，请重启后端，再执行同一准备命令；已保存的运行编号会继续配置，不重复创建。重复执行会复用本次研究的准备数据，不重置已确认配置。更换研究批次前应归档本地状态和证据，不覆盖既有记录。

首次准备与重复回归分别记录。默认对照为“逐条请求、核对、手动状态回填、导出”的脚本模拟，Agent 流程使用实际模型与实际 HTTP。脚本用时不等于真实人员劳动时间，也不据此计算人员效率提升比例。

前端可编辑操作及其返工按实际浏览器日志记录；脚本 API 调用单独标注，不伪装成鼠标点击或键盘输入。模型计量、接口、回填和报告耗时直接取持久化记录。

## 首次使用与重复回归

首次接入时，根据上面的接口资料配置方法、相对路径、headers/body/assertions 和依赖；资料准备及编写这些 JSON 的人工时间未测量。本场景用 `prepare.mjs` 建立共享请求基线，不能把脚本写入算作人员零成本准备。

在运行环境中设置 `http://localhost:8011`、独立账号邮箱、每轮不同的项目名称，认证变量名填 `BIZ_PASSWORD`、`BIZ_WRONG_PASSWORD`；对应值保存在后端 `TEST_AGENT_SECRET_<名称>`，`TEST_AGENT_SECRET_GRANTS` 仅授权本次控制项目使用。故意错误的密码也通过变量引用保存，真实请求仍与冻结用例一致。用例中使用 `{{BIZ_PASSWORD}}`，登录从 `/access_token` 提取 `BIZ_TOKEN`，后续请求头为 `Bearer {{BIZ_TOKEN}}`。创建项目、目录、用例依次提取 ID；`dependsOn` 填本次平台实际用例编号，不能直接照抄 fixture 内的 1–10。

1. 在测试运行内选中这 10 条用例，打开“接口测试 Agent”，整理测试计划。
2. 首次验收故意缺少查询用例配置。根据资料补充 GET `/cases/{{BIZ_CASE_ID}}`、认证头、状态码与字段断言、创建用例的前置编号；核实后清除对应待确认问题。
3. 勾选“同时保存执行配置到原用例”，保存并检查计划。修复前模型额外提出的问题按冻结规则核对，操作日志保留。
4. 核对请求、预期和测试环境，勾选两项确认后开始执行。任务完成时，测试用例中仍可以有失败和跳过。
5. 在报告勾选“仅看失败与未执行”，直接查看展开的断言差异与响应；导出本次 Excel。关闭面板后查看原运行统计和每行 Agent 来源，重开历史记录可复查。

重复回归时，在同一项目新建包含相同用例的运行，设置新的独立项目名称，其余认证与配置复用。当前版本对完整配置直接校验并进入“待确认执行”，省去重复生成和追问；缺失变量、前置依赖未选中、原预期待确认等仍会阻止执行。每次确认仍不可省略。若需要根据新接口说明重新准备，可在 Agent 面板提供该说明。

## 可复现采集

本次使用前端 8010、后端 8011，命令在仓库根目录执行。先配置管理员与 DeepSeek 环境并启动数据库、前后端；准备脚本设置认证变量后重启后端，再执行采集：

```powershell
node business/prepare.mjs
npx playwright install --no-shell chromium
node business/agent-study.mjs
node business/baseline-study.mjs
node business/summarize.mjs
```

修复后额外回归与最终证据核对：

```powershell
node business/prepare.mjs --reuse-check
node business/agent-study.mjs
node business/verify-evidence.mjs
node business/summarize.mjs
```

`--reuse-check` 额外创建第 4 个 Agent 运行；不会覆盖前三轮。已有完整证据直接保留。遇到 `.pending.json` 时先核对服务端任务和已发送请求，避免重复写业务数据；基线只有全部 HTTP 结果已采集时才支持 `node business/baseline-study.mjs --resume` 恢复 UI 阶段。Agent 未完成任务须按保留编号在平台中检查，不自动重建。

首轮包含预设缺失字段补充；后续执行配置已存回原用例。新版本采集会受“完整配置直接复用”修复影响，因此模型追问数不必复现修复前旧值。对比相同版本时应使用独立新批次，保留旧状态文件、测试账号与证据，不能覆盖本次材料。
