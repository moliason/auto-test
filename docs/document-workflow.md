# 接口文档到分轮验收报告

## 使用流程

1. 在项目中创建一个测试运行，可以暂时不添加用例。打开“接口测试 Agent”。
2. 配置并保存测试环境。目标来源必须列入后端 `TEST_AGENT_ALLOWED_ORIGINS`。密钥使用已授权的变量引用，沿用原项目密钥授权规则。
3. 任务来源选择“导入接口文档，生成用例并自动补测”，上传 UTF-8 Markdown 或 OpenAPI 3.0/3.1 JSON、YAML 文件，按需补充业务要求。
4. 设置预算并点击“从文档生成测试用例”。此时只调用模型、生成用例，不发送被测接口请求。
5. 查看请求、断言、前置依赖、规则及原文依据。生成的用例已加入项目下的专用目录和本次运行。可以编辑请求配置、缩小允许的接口范围、调整预算，再“保存并检查计划”。取消接口会排除它的用例；依赖缺失仍会阻止执行。
6. 核对范围、允许操作、预算、目标环境、认证和测试数据，勾选两项确认，再开始执行。
7. Agent 执行首批用例，读取真实证据，提出新的验证点。程序检查规则、范围、依赖、凭据、重复请求与预算；合法补测自动执行。原始预期和失败记录保留。
8. 查看“文档验收”、每轮用例与补测原因、具体请求响应及断言。Excel 新增“文档验收”工作表，与页面使用同一程序判定。

只有项目开发者及以上可以从文档生成用例、编辑和确认这类任务。环境仍由项目管理者维护；项目报告者及以上可以查看任务、导出报告、停止任务。

## 预算与停止

| 项目 | 默认 | 可设置范围与口径 |
| --- | --- | --- |
| 补测轮次 | 3 | 0–5；不含初始批次 |
| 用例数 | 20 | 1–20；本次执行计划中的初始与补测用例合计 |
| 模型调用 | 24 | 1–40；包含生成、分析及失败调用 |
| 执行时间 | 300 秒 | 1–600 秒；从用户确认执行开始 |

初始批次最多 6 条，其余文档内场景可在读取首轮结果后补测。文档最多 64 KiB、30 个接口；补充业务要求最多 6000 字符。引用仅支持文档内部 `$ref`，不访问外部 URL 或本地文件；对 YAML 别名、引用展开和结构深度设有上限。

停止原因包括没有新的有效验证点、轮次/用例/模型/时间预算耗尽、用户停止、执行故障、服务重启、需要补充规则或确认范围。工具调用总数另有 64 次保护上限。请求不跟随重定向，响应上限沿用 1 MiB。

“停止当前任务”会中断模型等待和正在进行的 HTTP 等待，并保存已有证据。已经发送的写请求可能已在被测服务生效，应核查结果后再创建新任务。服务重启不会自动重发请求。

超出范围、缺少执行所需的业务信息时进入“待补充信息”。使用“沿用文档补充要求”填入原文档，在补充要求中说明新规则，再创建新任务并重新确认。原任务的文档、已确认规则、原始失败和证据保持可追溯；不会原地修改已执行任务的预期。

## 用例和判定依据

每个规则对应一条可执行断言，并引用文档或补充要求中的原文。每个生成用例包含目的、正常/异常/边界场景、规则编号、请求配置、稳定依赖编号、生成理由、执行轮次及相关证据编号。程序将生成阶段的稳定编号转换成平台用例 ID。

准备阶段先提取整份文档的全部规则，再生成首批最多六条用例，供后续补测引用尚未执行的规则。模型生成的结构错误会返回模型修正，验证通过后才保存用例。确实缺少规则或执行配置的草稿会保留待确认问题。用户确认后，范围、规则、预算和初始用例编号会形成快照；补测不得更改这些规则。

规则覆盖表示对应请求已完成程序断言，**包含断言失败**。验收结果为：存在失败项、证据不足、已确认规则验证通过。预算中止不能视为完整验收。后续补测通过不会消除前面已经记录的失败。

文档规则抽取和自然语言解释仍需人工审核。程序能检查结构、原文引用、预期值、范围和执行证据，不能证明所有业务语义都被正确理解。AI 生成理由与原因推测须结合证据核查；数量、覆盖和状态以程序记录为准。

## 可重复演示

按根目录 README 启动数据库、前后端与 `node demo/server.mjs`，配置真实 DeepSeek 接口。新建独立运行，基地址为 `http://127.0.0.1:4010`，上传：

- [Markdown 示例](../demo/interface-testing.md)：八个明确场景，初始最多六条，读取结果后补齐剩余场景。完整覆盖时预期 **7 通过、1 失败**；总额断言预期 100，演示服务实际返回 90，应该保留失败。
- [OpenAPI YAML 示例](../demo/interface-testing.yaml)：验证参数、响应结构和总额规则解析；同样支持对应 OpenAPI JSON。

浏览器复现：

```powershell
npx playwright test --config playwright.agent.config.ts document-agent.spec.ts
```

依赖最近一次 `demo:seed` 产生的演示项目和本地账号。每次创建独立运行并保留历史；真实调用已配置的模型。截图、完整任务 JSON 和 Excel 存于忽略目录 `test-results/`。模型输出可能变化；不允许通过自动修改预期、删除失败或捏造模型结果使验收通过。

确定性的回归验证：

```powershell
npx vitest run --maxWorkers=2 --minWorkers=1
npm run build --prefix backend
npm run build --prefix frontend
```

`documentWorkflow.test.js` 使用固定模型工具响应和真实本地 HTTP，覆盖两轮反馈、重复候选、缺少信息、越界、范围缩小与恢复、每项预算、用户停止模型/HTTP 等待、请求故障、失败保留、项目权限及页面 API/Excel 判定一致。固定响应测试验证程序控制逻辑；真实模型浏览器验证单独记录。

本轮实际验收记录见 [document-workflow-check.json](verification/document-workflow-check.json)。本实验没有测量真实测试人员的效率，不把自动执行耗时换算成人工节省时间。
