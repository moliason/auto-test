## 对比方法

两种方式使用同一批用例、相同请求与断言、相同业务数据初始状态和权限。提前固定用例与预期版本，再分别执行人工流程与 Agent 流程。不能将首次配置成本混入一侧的重复回归，也不能把模型等待时间当作人工持续劳动。

- **首次使用**：从拿到已冻结的业务资料开始，到首轮证据与报告可供复核结束；记录环境配置、逐项请求/断言、认证与变量、计划审核和返工。
- **重复回归**：复用各自已确认配置，按相同数据恢复步骤开始；记录数据准备、执行、干预、回填、报告与复核。
- **操作步骤**：一次点击/勾选/选择计 1 次；一个字段的一次连续填写计 1 次，不按字符计数；切换页面或工具单独计数。导航、填写、确认和纠错分类记录，原始操作日志保留。
- **补充与干预**：补齐一个缺失字段/规则计 1 次；执行中为继续任务而进行的修改或重试另记 1 次。正常开始和结束操作不计作异常干预；同一操作不重复计入两个类别。
- **时间**：记录人工实际操作时间与系统等待时间，另记端到端墙钟时间。没有真实人工观测时留空，不按脚本运行速度推算人的速度。
- **实验来源**：真实测试人员、浏览器脚本模拟、后端自动化分别标注；脚本结果仅说明机械操作路径和系统性能，不代表真实人员效率。

三轮各自保存独立任务编号与报告。正确路径应完成“登录 → 业务操作 → 查询结果”；错误路径按文档明确的错误返回判断；前置故障路径验证后续不发送请求。为了验证断言检测而人为设置的错误预期必须标注，不能将其报告为系统真实缺陷。

| ---------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |

## 最终验收与检查

- 实际业务三轮与额外复测使用不同私有项目，所有预期判定满足冻结用例；七个运行状态均为审核中。
- 实际业务数据可从数据库支撑的查询接口读回；四个 Agent 任务的历史快照仍与执行后原始记录完全一致。
- 页面、原运行、历史和 Excel 一致；Excel 完整请求、响应、断言及模型/分项计时逐项读回核对。报告筛选后直接展开失败与跳过证据。
- 本阶段发现的完整配置重复追问已修复，仍保留双重确认和缺失信息阻断；265 项全仓库测试（60 个文件）通过，后端生产构建通过并已重启验证。前端本次业务接入未改源码，沿用此前已通过构建的生产版本。
- [业务说明](../business/README.md)提供首次补充、认证与依赖配置、重复回归、采集及复核命令。脚本采集故障已修复并在第 2、3 轮连续验证，中断证据保留。
- 结论限于单个本地业务系统与脚本操作路径；首次人工成本、真实人员效率、批量操作最优路径及其他业务适用性尚未验证。

## 分项耗时计量补充

已增加每条证据保存与原运行回填的事务耗时（包括提交），同时记录从读取完整测试结果到报告保存的整理耗时。重复 `execute_case` 命中已有结果时不重复记账，任务中止后写入的未执行结果也记录保存耗时；重启恢复的旧记录若没有计量，按覆盖次数显示缺失。

API 的 `executionMeasurements`、报告“执行与整理耗时”和 Excel“执行概览”使用同一个汇总。HTTP 统计只包含有请求记录的条目，前置失败跳过不算一次 HTTP 请求。保存覆盖以结果条数为分母，缺失记录保持未知，不能据局部数据计算完整耗时。报告整理与模型等待可能重叠，禁止将两者累加声称节省人工时间。
